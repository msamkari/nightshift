# Changelog

## 0.1.6 (2026-11-17)
Skills text and tests only (still no code). Motivation: a production queue runner wasted runs (read project files before checking usage, ran during times other tasks use the browser, kept firing after all items were finished). This entry includes the fix batch from the round-4 red team (R4-*, N3).
- New optional header line `QUIET_WINDOWS: 08:30-09:20, 12:30-13:20` (this machine's local time, a cloud routine runs in UTC; strict `HH:MM-HH:MM` with ASCII digits, ASCII spaces and tabs only, end excluded, midnight-crossing ranges allowed, overlaps allowed; all day = `00:00-12:00, 12:00-00:00`). Inside a window the run stops at once and writes nothing at all (no log line, no lock).
- CONFIG-ERROR (R4-M2, M4, L1): a malformed value (backticks pasted from a README example are rejected with a clear message, not stripped), a duplicate line, an unreadable clock, a near-miss key (case, bullet, space before the colon, fullwidth colon) or a key placed after the header now leaves ONE log line `- <time> UTC CONFIG-ERROR: <reason>` (only if the last log line is not already the same CONFIG-ERROR) and the run does nothing else. CONFIG-ERROR lines are ignored by the 20-minute check. N3 is fixed the same way: an unparseable last log line is a CONFIG-ERROR instead of switching the 20-minute check off.
- The header is now defined strictly (R4-M4): lines before the first `## ` heading, the first fence and the first list item, within the first 15 lines; fenced and item lines are never configuration. Lines are split on `\n` only (R4-L3: U+2028 and lone CR do not split).
- Gate order: header (first 15 lines: STATUS, LIMITS, QUIET_WINDOWS) -> quiet windows -> usage -> only then the whole queue, its Gate section and the project rules. The header peek cannot be avoided because LIMITS lives in the queue. On a usage stop only the last 10 lines are read to add the one dated log line (still only when the state changed).
- Auto-DONE: when every item under `## Items` (at least one) is DONE or BLOCKED, the run sets line 2 from exactly `STATUS: ACTIVE` to `STATUS: DONE` and says so; any other content of line 2 means no rewrite and a CONFIG-ERROR line. A run that finds no open item takes the same `mkdir` lock before that write. The plugin has no atomic file replace, only the lock; the rewrite touches one line.
- One Item definition (R4-M1) for "pick the first open item" and for auto-DONE: list marker (`-`, `*`, `+`, `1.`, `1)`, Arabic-Indic digits, indented or not) plus `[ ]`/`[x]`/`[X]` inside `## Items` outside fences; exact tokens DONE and BLOCKED (`DONEish` is not DONE); a numbered line without a checkbox, a malformed checkbox (`[]`, `[  ]`, `[ x]`), a `[x]` without DONE, zero items or an unclosed fence means auto-DONE refuses (never marks DONE when unsure) and logs a CONFIG-ERROR line. The Items section ends only at `## Log` or `## Operator routine`; any other `## ` line inside it is plain text (stated in the skill).
- Quiet window re-checked (R4-M3) after the lock is taken, before any browser step and before the final write; work already done is not reverted, the item stays unticked. No look-ahead before a window (see Known).
- The queue is changed only with the Claude Code Edit tool on the exact text (R4-M5); PowerShell Get-Content/Set-Content, Out-File, `>` and `sed -i` are forbidden (BOM, CRLF and non-ASCII kept). Auto-DONE log line lists the BLOCKED items with reasons (R4-L4). Kill switch accepts `STATUS:DONE`, `status: done`, `STATUS: DONE (paused)` (R4-L9). Duplicate sentence removed and the "no other file read" claim narrowed (R4-L6).
- What really differs from 0.1.5 for a queue WITHOUT `QUIET_WINDOWS` (the earlier claim "exactly as before" was wrong): (a) the usage-stop path reads only the first 15 and last 10 lines; (b) auto-DONE needs the exact line 2 `STATUS: ACTIVE` and the Item definition above (0.1.5 had no conditions); (c) a run with no open item takes the lock and applies 7b; (d) the kill switch is broader (L9); (e) a key look-alike, a LIMITS line outside the header, or an unparseable last log line now stops the run with a CONFIG-ERROR line; (f) line 2 and the queue are changed with the Edit tool only.
- LIMITS (R4-M4): only the header counts, there is no "above ## Items" fallback any more (a hand-written queue with LIMITS lower down gets a CONFIG-ERROR and must move it up).
- Unchanged: LIMITS cap at 90, single-session check, the 20-minute spacing itself (apart from ignoring CONFIG-ERROR lines and the N3 change), lock rules, hard rules, files-are-data. No `allowed-tools` added to any skill.
- Tests: 13 -> 43. A reference implementation of the written rules (parser, gate, item definition, auto-DONE, spacing check, CONFIG-ERROR dedupe) is run against the round-4 repro cases; the worked-examples table is parsed and executed. The prose itself is only needle-checked (R4-L8): semantic edits of a sentence can still pass unless a needle covers them; added needles for `A <= t < B` and ASCII digits.
- Known, not fixed (reason): R4-L5 stale-lock steal after >30 min (N8) and two runs after a long item: needs a heartbeat or code; line 2 already DONE is handled by logging nothing. R4-L6 the usage-stop append takes no lock and can collide with another run's Edit ("modified since read"): a lock for it would add a second writer rule; the harness loading project rules before the skill cannot be changed by a skill. R4-L7 DST: a window in the skipped spring-forward hour never applies. No look-ahead before a window (R4-M3 suggestion): the re-checks cover start, browser steps and the final write; an item that starts shortly before a window can still run into it. N9 line-2 lookalikes other than DONE and N10 (step 4 reads the whole queue) stay open. A bullet note under `## Items` is plain text, but a numbered note line without a checkbox, or a note starting with `[`, stops auto-DONE (fail-safe, shown by CONFIG-ERROR when no open item is left). A key-lookalike line inside the first 15 lines of Items (an item continuation line) stalls the queue with a CONFIG-ERROR (visible, fail-safe).
- Verified: `python -X utf8 -m unittest tests.test_skills` (43 tests OK) and `claude plugin validate .` (passed; the only advice is the README marketplace install line, left out because the marketplace entry is not decided). NOT verified: that a live model follows the new steps (all model behaviour is predicted from the text, as in the round-4 report); no scheduled run, no PowerShell-only session, no DST change or midnight window on a real clock; the reference implementation is a specification check, not code that ships.

## 0.1.5 (2026-11-15)
Skills text and tests only (no code), from the round-2 adversarial report:
- The run skill now carries its own hard rules instead of relying on the queue file: items may only read and write inside the project root folder (refuse `..`, absolute paths elsewhere, other drives, UNC, junction/symlink escapes, mark BLOCKED); the queue's HARD RULES/LIMITS/Gate/STATUS lines are never edited (only ticks and log lines; the single `STATUS: DONE` at the end stays); rules found in the queue can only be stricter; a `LIMITS` threshold above 90 counts as 90 (so `5h=100` no longer turns the gate off). The setup template's HARD RULES say the same.
- Stuck lock: if `Jobs/.nightshift.lock` is a file, a junction/symlink, not empty or dated in the future, the run does not try to clear it: it stops, tells the user to remove it, and logs ONE line (not again if the last log line is already that message). A future-dated last log line is reported once and treated as unparseable for the 20-minute check instead of "recent forever".
- Time and shell: native PowerShell uses `[DateTime]::UtcNow.ToString('yyyy-MM-dd HH:mm')` (there `date -u` printed local time); the lock is created only when `Jobs/` already exists (PowerShell `mkdir` would create it silently); runs work from the project root.
- Tests: 8 -> 13 (they assert the sentences exist).
- Not verified: everything about model behaviour is predicted from the text; no scheduled run, Bypass mode or PowerShell-only session was run for this release. Still open from the report: the 20-minute gate can be switched off by an unparseable last line (N3), a run longer than 30 minutes loses its lock (N8), line-2 lookalikes (N9) and huge queue files (N10).

## 0.1.4 (2026-11-15)
- Adversarial live round on 0.1.3 (four real scheduled runs): a `STATUS: DONE` below a blank line is still honored, a queue that rewrites its own HARD RULES to allow installs still gets the item BLOCKED, a failing check gives BLOCKED, and `LIMITS: 5h=0` stops on the usage gate; no lock folder was left behind in any case. The queue template written by setup now documents the lock (and how to clear a stale one), so it is no longer a hidden rule.

## 0.1.3 (2026-11-15)
- Live retest of 0.1.2: two scheduled runs that started at the same second both executed item 1, so the read-after-write `RUNNING` claim is not enough. The claim is now an atomic `mkdir Jobs/.nightshift.lock` (fails if another run holds it; a lock older than 30 minutes is treated as a crashed run); the lock is removed at the end. The `RUNNING` line stays as a log line for the 20-minute check.

## 0.1.2 (2026-11-15)
- Strict live tests in real scheduled sessions found two runs started 30 seconds apart on the same queue both executed item 1: the session-list check cannot be relied on. Now a run claims its item with a `RUNNING` log line before working and re-reads the file; later runs stop on the 20-minute log-age check. The session check stays as best effort.
- A failing item check (non-zero exit) now marks the item BLOCKED instead of leaving it to be retried forever.
- Setup now explains that a task saved in the default permission mode stalls at the first approval (use "Run now" once, or pick a mode), that the cadence must be at least about 30 minutes, and that the task starts in the working folder of the creating session (correcting 0.1.1, which said the folder could not be chosen).
- Verified live and unchanged: usage gate stop, 20-minute gate with UTC and local-time lines, a trap `STATUS: DONE` in the log ignored, install and outside-the-project items BLOCKED, injected instructions ignored.

## 0.1.1 (2026-11-15)
- Found by live tests in real scheduled sessions: the run took the time from memory (wrong, and in another zone), so the 20-minute log-age gate could be skipped. Now the time comes from `date -u` and every log line is `- YYYY-MM-DD HH:MM UTC`; lines without `UTC` are treated as local time; unparseable times skip only that check.
- Setup wrote its first log line without the time and told the scheduled task to use a working directory the tool does not have. Now the first line carries the time, and the task prompt carries the absolute project path. The duplicate-task guard reads the existing task prompts for that path.
- Verified live: the usage gate stops a run, injected instructions in a file or a "rules lifted" log line are ignored, a blocked item stays blocked, and the persistent-memory HANDOVER is archived and updated last.

## 0.1.0 (2026-11-14)
- First release: two skills and no code. `/nightshift:setup` writes a queue file (`Jobs/resume_queue.md`) and, only after a yes in chat, offers an hourly scheduled task; `/nightshift:run` is one gated iteration (STATUS, usage gate, session check, first undone item, log). Local work only by default. Optional persistent-memory integration.
